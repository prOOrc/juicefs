## ADDED Requirements

### Requirement: Провайдер синхронизации на Cloud Files API

Система SHALL предоставлять провайдер синхронизации Windows Cloud Files API в процессе Go: биндинг к `cldapi.dll` в пакете `pkg/cfapi` и движок в пакете `pkg/cfprovider`. Движок SHALL обращаться к `cldapi.dll` только через интерфейс, объявленный в `pkg/cfapi`, чтобы проверяться на подменной реализации без зарегистрированного sync root.

#### Scenario: Биндинг без cgo
- **WHEN** выполняется `go list -f "{{.CgoFiles}}" ./pkg/cfapi ./pkg/cfprovider`
- **THEN** для обоих пакетов вывод пуст

#### Scenario: Движок проверяется без Cloud Files API
- **WHEN** выполняется `go test ./pkg/cfprovider`
- **THEN** тесты очередей, отмены и классификации проходят на подменной реализации и не обращаются к `cldapi.dll`

### Requirement: Сверка layout структур биндинга

Пакет `pkg/cfapi` SHALL сверять размеры и смещения транскрибированных структур `CF_*` с эталонными значениями из `cldapi.h`. Источник, версия и SHA-256 файла SHALL быть записаны в `design.md`.

#### Scenario: Расхождение с эталоном
- **WHEN** размер или смещение любой структуры в `pkg/cfapi` отличается от эталонного значения
- **THEN** `go test ./pkg/cfapi` завершается ошибкой до первого вызова `cldapi.dll`

### Requirement: Обратные вызовы не блокируют

Функции, переданные в `CfConnectSyncRoot`, SHALL только копировать параметры в задание и ставить его в очередь. Обращения к hub, к диску и к `CfExecute` в них SHALL отсутствовать.

#### Scenario: Очередь без воркеров
- **WHEN** в тесте на диспетчер поступает 1000 событий FETCH_DATA при остановленных воркерах
- **THEN** все вызовы возвращаются суммарно менее чем за 1 секунду, счётчик операций ввода-вывода подменной реализации равен нулю

#### Scenario: Переполненная очередь
- **WHEN** очередь гидратации заполнена и поступает FETCH_DATA
- **THEN** задание не ставится в очередь и функция возвращает код ошибки

### Requirement: Регистрация sync root

Команда `juicefs clouddrive register` SHALL регистрировать каталог `%USERPROFILE%\AgioDrive` (флаг `--root`) через `CfRegisterSyncRoot` без идентичности пакета и SHALL создавать ключ реестра Explorer `SyncRootManager` с отображаемым именем. Повторная регистрация SHALL завершаться успешно без дублирования записей.

#### Scenario: Первая регистрация
- **WHEN** на томе NTFS выполняется `juicefs clouddrive register`
- **THEN** `juicefs clouddrive status` сообщает «зарегистрирован», каталог существует, ключ реестра содержит одну запись для этого sync root

#### Scenario: Повторная регистрация
- **WHEN** команда выполняется второй раз
- **THEN** код возврата 0, `status` сообщает «зарегистрирован», запись в реестре одна

#### Scenario: Корень не на NTFS
- **WHEN** `--root` указывает на каталог тома с файловой системой, отличной от NTFS
- **THEN** команда завершается с ненулевым кодом и именем файловой системы в сообщении, регистрация не выполняется

### Requirement: Отмена регистрации sync root

Команда `juicefs clouddrive unregister` SHALL удалять регистрацию sync root и его ключ реестра.

#### Scenario: Отмена регистрации
- **WHEN** выполняется `juicefs clouddrive unregister`
- **THEN** `status` сообщает «не зарегистрирован», ключ реестра отсутствует

### Requirement: Единственный экземпляр провайдера

На одном sync root SHALL работать не более одного процесса `juicefs clouddrive serve`.

#### Scenario: Второй экземпляр
- **WHEN** запущен `serve` и запускается второй `serve` с тем же `--root`
- **THEN** второй процесс завершается с ненулевым кодом до подключения к sync root, первый продолжает обслуживание

### Requirement: Маркер готовности sync root

`serve` SHALL выводить в лог строку `OK, <имя тома> is ready` ровно один раз за запуск — после подтверждения регистрации, установки соединения и создания плейсхолдеров верхнего уровня.

#### Scenario: Готовность
- **WHEN** соединение установлено и плейсхолдеры верхнего уровня созданы
- **THEN** строка-маркер присутствует в логе один раз

#### Scenario: Hub недоступен
- **WHEN** `serve` запущен при недоступном hub
- **THEN** маркер в логе отсутствует, процесс продолжает попытки подключения

### Requirement: Плейсхолдеры из метаданных hub

Провайдер SHALL создавать плейсхолдеры записей backend: верхнего уровня — при готовности; записи каталога — при первом обращении к каталогу. Идентификатором плейсхолдера SHALL служить inode записи в backend. Размер и время изменения плейсхолдера SHALL совпадать с метаданными backend.

#### Scenario: Верхний уровень
- **WHEN** `serve` готов
- **THEN** `cmd /c dir "%USERPROFILE%\AgioDrive"` перечисляет те же записи, что и `juicefs clouddrive ls /`, с теми же размерами файлов

#### Scenario: Дочерний каталог
- **WHEN** выполняется `cmd /c dir "%USERPROFILE%\AgioDrive\<каталог>"`
- **THEN** перечисляются записи, которые возвращает `juicefs clouddrive ls /<каталог>`

#### Scenario: Перезапуск без дублей
- **WHEN** `serve` перезапускается
- **THEN** каждая запись каталога присутствует на диске один раз

### Requirement: Локальные файлы не перезаписываются

Провайдер SHALL NOT перезаписывать и SHALL NOT удалять локальный файл, не являющийся плейсхолдером, при создании плейсхолдеров и при сверке.

#### Scenario: Одноимённый локальный файл
- **WHEN** в sync root лежит локальный файл с именем записи backend
- **THEN** файл остаётся на диске без изменений, в логе есть запись о конфликте

### Requirement: Гидратация по требованию

По запросу FETCH_DATA провайдер SHALL читать данные через `pkg/fs` и передавать их одним вызовом `CfExecute(TRANSFER_DATA)` в страница-выровненном буфере. Каждое задание SHALL завершаться ровно одним `CfExecute`.

#### Scenario: Содержимое совпадает с backend
- **WHEN** вычисляется `sha256sum` файла размером не менее 1 GiB в sync root
- **THEN** результат совпадает с `juicefs clouddrive hash <путь>`

#### Scenario: Частичная гидратация
- **WHEN** читаются первые 4 MiB файла размером не менее 1 GiB
- **THEN** свободное место тома уменьшается менее чем на четверть логического размера файла

#### Scenario: Ровно один ответ на задание
- **WHEN** в тесте задание проходит любые ветви завершения
- **THEN** `CfExecute` вызван для задания ровно один раз

### Requirement: Отмена гидратации

CANCEL_FETCH_DATA SHALL останавливать задание между порциями чтения. Буфер задания SHALL возвращаться в пул.

#### Scenario: Прерванное чтение
- **WHEN** начато чтение крупного файла и дескриптор закрывается до завершения
- **THEN** поступает CANCEL_FETCH_DATA, задание отвечает статусом отмены, число горутин процесса возвращается к значению до чтения

### Requirement: Pin и unpin

Команды `juicefs clouddrive pin` и `unpin` SHALL вызывать `CfSetPinState`; флаг `--recursive` SHALL применять состояние к каталогу рекурсивно. Состояние pin SHALL сохраняться между перезапусками провайдера.

#### Scenario: Pin файла и чтение без провайдера
- **WHEN** выполнен `pin` файла, процесс `serve` завершён, сеть отключена
- **THEN** файл читается целиком, `sha256sum` совпадает с исходным

#### Scenario: Pin каталога
- **WHEN** выполнен `pin <каталог> --recursive`
- **THEN** все файлы каталога гидратированы и читаются после завершения `serve`

#### Scenario: Unpin
- **WHEN** выполнен `unpin` файла
- **THEN** запись остаётся в каталоге, занятый файлом объём на диске меньше логического размера

### Requirement: Выгрузка новых и изменённых файлов

После закрытия последнего дескриптора нового или изменённого файла провайдер SHALL выгрузить содержимое локального файла в backend через write-API `pkg/fs`. Затем он SHALL преобразовать новый файл в плейсхолдер либо обновить существующий, пометив его синхронизированным.

#### Scenario: Новый файл
- **WHEN** в sync root создаётся файл и его дескриптор закрывается
- **THEN** `juicefs clouddrive hash <путь>` совпадает с SHA-256 исходного файла, `juicefs clouddrive status <путь>` сообщает «плейсхолдер, in-sync»

#### Scenario: Изменённый плейсхолдер
- **WHEN** приложение изменяет плейсхолдер и закрывает файл
- **THEN** `hash` возвращает хеш нового содержимого, `status <путь>` сообщает in-sync

#### Scenario: Обрыв выгрузки
- **WHEN** процесс `serve` завершается во время выгрузки файла
- **THEN** backend не содержит частичной версии файла, после повторного запуска файл выгружается и `hash` совпадает с локальным

### Requirement: Атомарность версии файла при выгрузке

Версия файла SHALL становиться видимой в backend одним подтверждением метаданных при `Flush` write-API `pkg/fs`. Отложенная выгрузка (write-back) SHALL быть отключена.

#### Scenario: Видимость версии
- **WHEN** выполняется выгрузка файла
- **THEN** до завершения `Flush` `hash` возвращает хеш предыдущей версии либо «не найден», после завершения — хеш новой версии

### Requirement: Распространение удалений, переименований и создания каталогов

Удаление, переименование и создание каталога в sync root SHALL передаваться в backend только для записей, известных провайдеру как плейсхолдеры. Удаление sync root SHALL NOT передаваться в backend.

#### Scenario: Удаление плейсхолдера
- **WHEN** пользователь удаляет файл-плейсхолдер
- **THEN** `juicefs clouddrive ls <каталог>` больше не содержит запись

#### Scenario: Удаление локального файла до выгрузки
- **WHEN** удаляется новый локальный файл до завершения выгрузки
- **THEN** `ls` не содержит запись, задание выгрузки отменено

#### Scenario: Переименование
- **WHEN** переименовывается плейсхолдер
- **THEN** `ls` показывает запись под новым именем без старого

#### Scenario: Новый каталог
- **WHEN** в sync root создаётся каталог
- **THEN** `ls` родительского каталога содержит его

#### Scenario: Удаление sync root
- **WHEN** пользователь удаляет каталог sync root
- **THEN** `ls /` не пуст, при повторном запуске `serve` каталог пересоздаётся и регистрация действует

### Requirement: Отложенные операции при недоступном hub

Операция записи, не выполненная из-за недоступности hub, SHALL сохраняться в журнале каталога состояния и повторяться с нарастающей паузой до успеха, в том числе после перезапуска `serve`. Локальная копия файла SHALL оставаться на диске до успешного подтверждения.

#### Scenario: Создание офлайн
- **WHEN** файл создаётся при недоступном hub, затем `serve` перезапускается после восстановления доступа
- **THEN** `hash` совпадает с локальным файлом, `status <путь>` сообщает in-sync, журнал не содержит операций

#### Scenario: Удаление офлайн
- **WHEN** плейсхолдер удаляется при недоступном hub, затем доступ восстанавливается
- **THEN** после повтора `ls` не содержит запись

### Requirement: Сверка при старте

При запуске `serve` SHALL ставить в очередь выгрузки локальные файлы без плейсхолдера и плейсхолдеры вне состояния in-sync, а в очередь удаления — записи индекса, отсутствующие на диске в каталогах с завершённым наполнением.

#### Scenario: Восстановление после сбоя
- **WHEN** `serve` запускается после сбоя, в sync root есть изменённый плейсхолдер вне in-sync и удалённый плейсхолдер в наполненном каталоге
- **THEN** первый выгружается, второй удаляется в backend

### Requirement: Изоляция пула гидратации

Гидратация и выгрузка SHALL выполняться разными пулами. Воркеры гидратации SHALL NOT вызывать `CfHydratePlaceholder`, `CfSetPinState` и write-API `pkg/fs`.

#### Scenario: Выгрузка ожидает гидратации
- **WHEN** в тесте все воркеры выгрузки ожидают данных гидратации
- **THEN** задания FETCH_DATA продолжают выполняться

### Requirement: Режим без записи

Флаг `--read-only` команды `serve` SHALL отключать передачу локальных изменений в backend.

#### Scenario: Файл в режиме без записи
- **WHEN** `serve --read-only` и в sync root создаётся файл
- **THEN** `ls` не содержит запись, файл остаётся на диске без изменений

### Requirement: Сборка прототипа с CGO

Прототип SHALL собираться командой `CGO_ENABLED=1 go build ./cmd` под mingw gcc без изменений `pkg/compress`.

#### Scenario: Сборка
- **WHEN** выполняется `CGO_ENABLED=1 go build ./cmd`
- **THEN** исполняемый файл создан, `git diff agio-drive-v2 -- pkg/compress` пуст

### Requirement: Использование существующих механизмов доступа

Доступ к метаданным SHALL выполняться через `meta.NewClient` с URI `grpc://` и параметрами `oidc-*`. Учётные данные объектного хранилища SHALL получаться теми же STS-провайдерами, что в `juicefs mount` (`cmd/render_mount.go`, `cmd/sts_refresher.go`). Bucket и параметры хранения SHALL браться из format, отданного hub. Новый код получения учётных данных SHALL отсутствовать.

#### Scenario: Механизмы доступа не изменены
- **WHEN** выполняется `git diff agio-drive-v2 -- pkg/meta pkg/chunk cmd/sts_refresher.go`
- **THEN** вывод пуст, в каталоге `specs/` этого change есть только `domain-cfapi-provider`
