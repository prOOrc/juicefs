# Design: implement-windows-mount

## Context

Исследование (explore, 2026-10-03, три explorer-отчёта) показало: `grpcMeta`-клиент платформенно-нейтрален (регистрация в общем реестре `pkg/meta/grpc_client.go:240`, dial `:190`, FEK-кеш, HubState, wipe/reconnect — без build-тегов); WinFsp-маунт работает и покрыт CI `wintest.yml` (с redis); OIDC (token manager `pkg/oidc/token_manager.go`, библиотека `prOOrc/oidc-login` — pure Go, token cache на диске `$HOME/.oidc-login`, браузер через `pkg/browser`) и шифрование (stdlib crypto, FEK в RAM LRU) кроссплатформенны. Блокер один: флаги `--sts-enabled`/`--company-id` только в `cmd/mount_unix.go:503-510`. Мотивация — proposal.md.

## Goals / Non-Goals

**Goals**: рабочая связка «Windows + `grpc://` + OIDC (interactive) + шифрование + STS», подтверждённая прогоном на реальной Windows-машине; спеченный контракт `domain-windows-mount`.

**Non-Goals** (дублируют proposal; здесь только дизайн-границы): не меняем `cmd/mount.go` и `pkg/meta` — паритет достигается декларацией флагов в Windows-flagset, вся обработка уже в общем коде; не меняем `pkg/winfsp` кроме теста реконструкции (если тест выявит дефект — фикс отдельной задачей по факту).

## Component Map

|---|---|---|

| Общий STS-флоу | `cmd/mount.go:726-755` | Не меняется: type assert `StsProxyClient()`, `refresher.Start()` fail-fast — заработает на Windows сразу после флагов |

## Execution Flow

1. **Flags parity** (задача 1): в flagset `cmd/mount_windows.go` добавить оба флага. Общая обработка в `cmd/mount.go:726-755` уже требует encrypted volume + `grpc://` + `StsProxyClient` и делает fail-fast — на Windows сработает без изменений.
2. **Первый вход** (задача 2, прогон): интерактивный `juicefs mount grpc://... Z:` с пустым `$HOME/.oidc-login` — браузер → localhost callback → маунт завершается. Повторный маунт — токен из кеша, без браузера.
3. **Service mode** (задача 3): `-d` → `RunAsSystemService` пишет CommandLine в реестр; unit-тест реконструкции (парсер `:1365-1424`) фиксирует: URL с query-параметрами и оба STS-флага сохраняются байт-в-байт. Прогон: перезапуск сервиса — коннект с той же конфигурацией.
4. **E2E** (задача 4): на stage/виртуальной Windows: маунт зашифрованного волюма с STS, чтение/запись/расшифрование, wipe по logout, offline-поведение (heartbeat → wipe ключей по permission generation).
5. **CI** (задача 5, решение по итогам): если прогон 4 автоматизируем — grpc://-сценарий в `wintest.yml`; иначе фиксируем «ручной прогон» и вердикт в change (решение документируется в tasks-чекбоксе).

## Invariants

- **Общий код не ветвится**: `cmd/mount.go`, `pkg/meta`, `pkg/vfs` не получают GOOS-условий; платформенная разница живёт только в `cmd/mount_windows.go` (декларация флагов) и существующих Windows-заглушках.
- **Дефолт Windows-маунта не меняется**: без `--sts-enabled`/`--company-id` поведение Windows-маунта идентично текущему (флаги опциональны).
- **Семантика STS едина**: fail-fast без фолбэка — тот же контракт, что на Linux (domain-encrypt, требование «Data-plane STS credentials»); паритет — копирование декларации, не новая семантика.
- **Метаданные движков не затрагиваются** — parity Redis/SQL/KV не применима (change не трогает `pkg/meta`).

## Decisions & Rationale

1. **Копия деклараций флагов в `mount_windows.go`, а не вынос в общий файл** — `mountFlags` Windows и Unix уже разведены по платформам; попытка унифицировать flagset — рефактор вне скоупа с риском для обоих CLI. Альтернатива (общий `stsFlags()`-хелпер) возможна позже; не блокирует.
2. **Интерактивный вход как единственный поддерживаемый сценарий первой фазы** — решение пользователя (2026-10-03); device-code/prepopulated-cache — следующая фаза. В спеке фиксируем контракт «не виснем»: попытка аутентификации вне интерактивной сессии завершается по таймауту библиотеки с ясной ошибкой (поведение oauth2cli — таймаут ожидания callback; верифицируется прогоном, см. Open Questions).
3. **Unit-тест на реконструкцию URL вместо доверия «формально сохранит»** — исследование пометило `winfs.go:1365-1424` как непроверенное для query-параметров; регрессия здесь ломает OIDC/STS в сервисном режиме незаметно. Тест дешёвый, гоняется Windows-раннером.
4. **CI-решение отложено в apply** — e2e grpc:// требует OIDC-провайдера и зашифрованного волюма; если в CI это не поднимается без stage-зависимостей, фиксируем ручной прогон как верификацию фазы (честнее, чем хрупкий fake).

## Integration Points

- **`implement-grpc-tls`**: не кодовая зависимость; после вливания TLS-change Windows-верификация повторяется с `tls=1&tls-ca=...` в URL (реконструкция в service mode уже покрыта тестом задачи 3 — параметр `tls*` в числе проверяемых).
- **`implement-encrypt`**: STS-флоу, wipe/logout, permission generation — контракт дельты `domain-encrypt`; Windows-прогон верифицирует те же требования на второй платформе (новых требований шифрованию не добавляем).
- **Эксплуатация agio Drive**: инструкция первого входа (интерактивная сессия → браузер) и ограничение сервисного режима (прогретый кеш) — часть rollout-заметок Windows-фазы.

## Risks / Trade-offs

- [Сервисный OIDC-flow вне интерактивной сессии: реальное поведение oauth2cli при отсутствии браузера не подтверждено] → прогон задачи 2/3 фиксирует фактический таймаут; если маунт висит дольше разумного — отдельный фикс-таск по факту (в пределах фазы).
- [Реконструкция CommandLine в реестре может терять экранирование спецсимволов URL (`&`, `=`)] → unit-тест задачи 3 гоняет URL с полным набором query-параметров; дефект чинится в рамках фазы.
- [Стенд Windows для e2e: нужен реальный proxy+OIDC+шифрование] → прогон на stage-топологии (как гейты 10.7 `implement-encrypt`); без стенда задачи 2/4 не закрываются — эскалация пользователю.
- [Многопользовательский терминальный сервер: токен-кеш в `$HOME` на пользователя] → ок для первой фазы (каждый маунт — от пользователя с его кешем); общий кеш не нужен до сервисного сценария.

## Open Questions

- Фактический таймаут oauth2cli без браузера в сервисном контексте (измеряется прогоном; влияет на формулировку ошибки, не на спеку).
- Автоматизировать ли e2e grpc:// в `wintest.yml` (решение задачи 5 по итогам ручного прогона).
