# Design: fix-meta-proxy-session-churn

## Context

Симптом и механизм — см. proposal.md. Решение принято по результатам
source-инвестигации (explorer 2026-11-01) и архитектурного вердикта.

## Goals / Non-Goals

- Goal: ФС остаётся доступной для живого клиента после рестарта прокси
  (и после eviction из path-кэша) без перемонтирования.
- Goal: fail-closed семантика authz сохранена полностью.
- Non-Goal: client-provided paths (отдельный change; комментарий
  pkg/meta/inode_path_cache.go:34-37).
- Non-Goal: per-session chroot-изоляция общего engine (отдельный change).
- Non-Goal: клиентский полный re-establish (re-Load/NewSession/purge) —
  тяжёлый протокол, требует обновления клиентов; прокси-рекавери покрывает
  проблему.

## Decisions

### D1. Прокси-рекавери по parent chain (ядро фикса)

На cache miss перед fail-closed deny — серверная реконструкция пути:
подъём по `attr.Parent` через ПРЯМЫЕ чтения engine (минуя authz-интерсептор;
образец — `baseMeta.GetPaths`, pkg/meta/base.go:2498-2547). Источник истины
о структуре — engine; кэш остаётся производной структурой.

Инварианты:
- **I1 изолированность**: рекавери — только внутренние чтения engine;
  клиентская идентичность не участвует; authz-прав пользователя на чужие
  пути не требуются (реконструируется серверный факт, а не выполняется
  клиентская операция).
- **I2 fail-closed сохранён**: рекавери никогда не предоставляет доступ;
  результат — лишь вход для существующего authz-решения.
- **I3 fail-closed при неудаче**: CYCLE / превышение глубины / ошибка
  engine → тот же deny, что сегодня при промахе.
- **I7 ENOENT ≠ неопределённость**: engine сообщил «инода нет» → клиенту
  ENOENT (честный POSIX-ответ на устаревший инод), не deny.
- **I5 потокобезопасность**: не более одной in-flight реконструкции на инод
  (singleflight, golang.org/x/sync/singleflight); прогрев предков через
  PutIfAbsent схлопывает «стадо» на общих родителях.
- **I6 ограниченность**: depth cap (`maxRecoverDepth`, 64) + visited-set;
  завершимость за O(depth) чтений.
- **I8 без storm**: ленивый рекавери по промаху; никакого eager warm-up
  при старте прокси.

Точки встраивания (все inode-only call sites): GetAttr/Open/Access/
NewDirHandler (cache.Get miss → resolve), Lookup (parent miss → resolve до
BuildChildPath), Open-FEK/ResolveFileKey (path=="" → resolve), Readdir
(resolve(dirIno)).

### D2. Readdir: EACCES вместо тихого пустого листинга

`filterEntriesByAuthz`: parentPath нерезолвим даже после рекавери → EACCES.
Пустой листинг легитимен только при известном пути и 0 авторизованных
детях. Мотивация: «пустой каталог с errno 0» выглядит как уничтожение
данных — худшая форма бага.

### D3. Errno-маппинг клиента

Lookup/GetAttr/NewDirHandler переводят gRPC-статус через
`grpcStatusToErrno` (PermissionDenied/Unauthenticated → EACCES, NotFound →
ENOENT, прочее → EIO) вместо безусловного EIO. Это меняет наблюдаемые
errno (EIO → EACCES) — POSIX-корректно; обновляются ассерты существующих
тестов в этом же change.

### D4. Клиентские хуки реконнекта (минимальные)

- EBADF от DirHandler-операции → дроп локального хендла; пересоздание на
  следующем readdir(off==0) — существующий механизм vfs (vfs.go:480-504).
- Re-Chroot при переходе offline→online (markHubOnline), строго ДО replay
  write journal, только при сконфигурированном subdir. Политическое
  допущение: один subdir на прокси-деплой (иначе текущее поведение уже
  сломано — последний Chroot выигрывает для всех клиентов); stage subdir
  не использует. Полная изоляция — отдельный change.

### D5. Точечная инвалидация мутациями

Rename/Unlink/Rmdir в пост-колле → `resolver.Invalidate(ino)`. Устаревание
кэшей ПОТОМКОВ переименованного каталога до eviction — задокументированное
ограничение (следующий рекавери по attr.Parent чинит точечно).

## Risks / Trade-offs

- [Нагрузка на engine при масс-рестарте] → I6/I8 (cap, singleflight,
  прогрев предков, ленивость); worst case O(различные иноды × глубина),
  размазано по промахам.
- [Рекурсия authz при рекавери] → интерсептор висит на gRPC-пути, а не на
  внутренних вызовах engine; coder обязан подтвердить первым шагом T2.
- [EIO→EACCES виден клиентам] → намеренное улучшение диагностики; ядро FUSE
  обрабатывает EACCES корректно.
- [Re-Chroot при нескольких subdir-клиентах за одним прокси] → гейт D4;
  зафиксировано как допущение.

## Migration Plan

Деплой нового прокси чинит живых клиентов без перемонтирования (серверный
фикс). Клиентские части (D3/D4) едут в обычном цикле обновления образов.
Порядок не критичен: старый клиент + новый прокси — уже починено ядром;
новый клиент + старый прокси — поведение как сейчас.
