# ADR: Outbox — события по дочерним объектам при move/rename/delete директории

## Контекст

Outbox (ветка `outbox`) публикует события файловой системы в Redis Streams, откуда standalone-консьюмер (`juicefs outbox`) пересылает их в Kafka-топик `juicefs.events`. События генерируются на уровне meta-операций (`pkg/meta/redis_event.go` → `publish*ToPipe`), типы — в `pkg/meta/events.go`: `FileCreated`, `FileDeleted`, `FileMoved`, `FileWritten`, `DirCreated`, `DirDeleted`, `DirMoved`.

Потребители строят path-based проекции (например, `drive_object` в agio-platform: полный путь файла, поиск, аналитика, привязка прав). Для корректности такой проекции каждое изменение пути объекта должно приходить событием.

### Фактическое состояние (as-is, ветка outbox)

- **Move/rename директории** (`doRename`, `pkg/meta/redis.go`): поддерево перемещается атомарно в одной Redis-транзакции — меняется только entry родительского inode, inode детей не меняются. Публикуется **одно** событие `DirMoved` для самой директории; по дочерним объектам (файлы и вложенные директории на любой глубине) события **не публикуются**.
- **Удаление**: `doRmdir` возвращает `ENOTEMPTY` для непустой директории — удаление поддерева всегда идёт через пообъектные meta-вызовы (unlink/rmdir на каждый объект), и каждый из них публикует своё событие (`FileDeleted`/`DirDeleted`). Группирующего маркера «поддерево удалено» нет; будущие bulk-пути удаления (включая очистку trash) могут не публиковать события по детям.

### Проблема

После move/rename директории path-based проекция потребителя дрифтует: пути всех вложенных объектов в проекции остаются старыми, пока на них не произойдёт отдельная операция. Для agio Drive это ломает поиск по пути, привязку `drive_object_permission` и audit-логи.

## Варианты

### Вариант 1: События по каждому дочернему объекту (producer-side enumeration)

При move/rename директории meta-слой рекурсивно перечисляет поддерево и публикует `FileMoved`/`DirMoved` (с `old_path`/новым путём) на каждый потомок; при удалении — гарантирует `FileDeleted`/`DirDeleted` по всем потомкам на всех путях удаления.

Плюсы:
- Потребитель остаётся тупым: применяет события один за другим, без собственного обхода метаданных.
- Единая модель для всех операций — проекция всегда сходится.

Минусы:
- Стоимость пропорциональна размеру поддерева: перечисление в Redis + N событий в одном pipeline.
- Большой move (100k файлов) = 100k событий; нужны ограничения/чанки и оценка нагрузки на stream.

### Вариант 2: Только `DirMoved`, потребитель сам разрешает поддерево

Producer публикует одно событие, потребитель при получении `DirMoved`/`DirDeleted` сам обходит метаданные (через Meta Proxy / Redis) и обновляет проекцию.

Плюсы:
- Минимальный объём событий в потоке.

Минусы:
- Потребитель получает зависимость от live-метаданных: на момент обработки события дерево уже могло измениться (race) — проекция может зафиксировать состояние, которого не было.
- Дублирует логику перечисления в каждом потребителе; нарушает принцип «событие = самодостаточный факт».

### Вариант 3: Гибрид — `DirMoved` + маркер поддерева, перечисление опционально

Публикуется `DirMoved` с флагом/списком «поддерево затронуто»; потребитель либо применяет пообъектные события (если они есть), либо сам разрешает поддерево.

Минусы: две модели применения — сложнее для потребителей; не решает race варианта 2 полностью.

## Решение (draft)

Выбран **Вариант 1**: producer-side enumeration — при move/rename директории публикуются события по каждому дочернему объекту; при удалении гарантируются события по всем потомкам на всех путях удаления.

Предварительные параметры (уточняются в OpenSpec change):

- Типы событий для детей: `FileMoved`/`DirMoved` с корректными `old_path` и новым путём (move/rename); `FileDeleted`/`DirDeleted` (удаление).
- События детей пишутся в тот же Redis pipeline, что и родительская операция (`publishEventToPipe`) — атомарность с meta-транзакцией.
- Порядок: сначала потомки, затем родительское событие (`DirMoved`/`DirDeleted`) — потребитель к моменту родительского события видит полное поддерево. (Открытый вопрос.)

## Последствия

- Move/rename большой директории становится дороже: O(размер поддерева) по Redis-чтениям и событиям.
- Потребители обязаны быть идемпотентными и обрабатывать события в порядке stream.
- Объём `juicefs.events` вырастет при операциях с большими деревьями — проверить метрики и лимиты stream.

## Открытые вопросы

- [ ] Лимит размера поддерева для одного pipeline: чанковать перечисление (несколько транзакций) или единый pipeline? Как сохранить атомарность при чанковании?
- [ ] Порядок событий (потомки → родитель vs родитель → потомки) — зафиксировать в spec.
- [ ] Нужен ли группирующий маркер (batch/subtree ID) в событиях для метрик и отладки?
- [ ] Trash: события при перемещении в trash и при очистке trash — по текущей модели или как отдельный тип?
- [ ] Parity: outbox сейчас реализован только для `redisMeta`. Требовать ли child events для SQL/KV движков (у них outbox отсутствует) — зафиксировать scope.

## Связь с OpenSpec

После принятия ADR создаётся OpenSpec change по капабилити `domain-outbox` (delta-спеки: события по дочерним объектам). До принятия — статус draft, реализация не начинается.
